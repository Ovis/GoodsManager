# GoodsManager

複数のコレクションに分けて商品と所持品を管理する、個人向けのWebアプリです。商品情報と写真を登録し、所持数・状態・保管場所や個体ごとのメモをまとめて管理できます。

React・バーコード読み取り・SQLite・SkiaSharpなどのライセンスと著作権表示は、配布物の `notices/application/`（Dockerでは `/app/notices/application/`）に同梱しています。ブラウザー向けライブラリの表示は配信するJavaScriptにも含めています。写真の文字読み取りについては `PhotoOcrAssets/notices/` に別途収録しています。

バックアップのマニフェストには、版番号とソース識別情報を含むビルドの版を記録します。Dockerイメージのビルド引数 `APP_VERSION`（既定 `1.0.0`）と `SOURCE_REVISION` で指定でき、`SOURCE_REVISION` を省略した場合はビルド対象ソースからSHA-256を計算して付けます。

## できること

- コレクションの作成・名前変更・切り替えと、分類などの設定コピー
- 商品の登録・検索・編集と写真の管理
- カメラでのバーコード読み取り、ISBNからの書籍情報取得
- 商品登録時の写真からの文字読み取りとコピー
- カテゴリ・作品・キャラクター・タグ・メーカー・販売元による整理
- 所持数、状態、保管場所、購入先、個体ごとのメモ・写真の管理
- 重複候補の確認、マスターの整理、ゴミ箱への移動と復元
- 自動・手動バックアップと、アプリ停止中の復元
- ログインID・パスワードの変更と、パスキーの登録・名前変更・削除

## 利用の流れ

1. 公開HTTPS URLを開きます。アカウントがない場合は自動で初期登録画面が開くので、初期登録トークン・ログインID・パスワード・パスワード確認を入力します。登録後は自動でログインします。次回からは設定したIDとパスワード、または登録済みのパスキーでログインできます。
2. 「商品を登録」で商品情報・所持数・写真を入力します。重複候補が出た場合は、別の商品として登録するか既存商品へ追加するかを確認します。
3. 「コレクション」で検索・絞り込みを行い、商品詳細から商品情報や所持品を編集します。
4. 「設定」→「マスター管理」で、選択中のコレクションの分類や関連情報を整理します。ゴミ箱に移した商品は「ゴミ箱」から復元でき、完全削除すると元に戻せません。
5. 管理者は「設定」→「バックアップ」で自動実行の設定と履歴を確認し、必要に応じて手動実行・ダウンロードを行います。
6. 「設定」→「アカウント設定」で、パスワードの変更やパスキーの登録・名前変更・削除を行います。パスワード変更とパスキーの追加・削除には、現在のパスワードまたは登録済みパスキーによる本人確認が必要です。

画面からのアカウント作成は初期登録の1件だけです。初期登録が済んでいる場合はログイン画面へ案内します。最初のアカウントがアプリ管理者となり、「マイコレクション」が用意されます。

初期登録トークンは、アカウントがない初回起動時にデータ保存先の `setup-token.txt`（Dockerコンテナ内では `/data/setup-token.txt`）へ作成します。管理者だけがアクセスできる端末から、ホスト側のデータ保存先にあるこのファイルを安全なテキストエディターで開き、1行目を画面の「初期登録トークン」へ入力してください。2行目は有効期限です。ターミナルへの表示・コマンド引数・URL・チャット・共有クリップボード・Gitへの貼り付けは避けてください。Linuxではファイルを実行ユーザーのみ読み書きできる権限で作成します。

トークンの有効期限は発行から24時間で、期限内の再起動では同じ値を維持します。期限切れの場合はアプリを再起動すると再発行します。入力エラーでは消費せず、登録成功後に失効・削除します。Web応答・アプリのログ・アプリが作成するバックアップには含めません。ファイルが破損して起動できない場合は、アプリ停止中に管理者がこのファイルだけを取り除いて再起動してください。既存アカウントがある環境で初期登録をやり直す必要はありません。

PCでは左サイドバーの下部、スマートフォンでは画面上部でコレクションを切り替えます。「設定」→「コレクション管理」で作成・名前変更を行います。商品・所持品・ゴミ箱・マスター・画像変換設定はコレクションごとに独立します。新しいコレクションは空で作成するか、参加中のコレクションから6種のマスター・関連・カテゴリ階層・並び順・画像変換設定をコピーできます。商品・所持品・写真はコピーせず、コピー後の設定も元の変更には追従しません。

同じタブでコレクションを切り替えても、登録・編集の下書きはそれぞれ保持します。下書きはページを閉じたり再読み込みしたりすると失われます。複数タブでは別々のコレクションを開けます。利用者の追加・招待・権限変更の画面はまだありません。

コレクションの表示形式（ギャラリー／表）・1ページの件数・並び順を変更すると、そのブラウザに即時保存し、次に開く一覧の既定値にします。コレクション間で共通の設定です。URLに表示条件が指定されている場合はそちらを優先し、戻る・進むでは各履歴の条件を復元します。並び順を一度も保存していない場合は、検索語ありで関連順、なしで登録日が新しい順になります。ブラウザの保存データを削除すると表示設定も初期化されます。

「設定」→「画像設定」で、選択中のコレクションの原本保持・表示用画像とサムネイルの長辺／品質を変更し、アップロード上限を確認できます。変更後に新しくアップロードする写真から適用され、保存済みの写真は再変換しません。

商品登録で写真を追加すると、ブラウザー内で文字を読み取ります。「読み取り結果を見る」を押すと、写真とコピー用のテキストを表示します。複数の写真は同じ結果画面で切り替えられ、閉じた後も再表示できます。必要な部分をコピーし、商品名などへ貼り付けてください。商品情報への自動入力や、読み取り結果の保存は行いません。読み取りに失敗しても写真の添付・商品登録は続けられます。

初回の文字読み取りにはモデルの読み込み時間がかかります。外部のOCRサービスへ写真を送ることはなく、モデルもこのアプリから取得します。通常の写真アップロードは行います。画面を離れると読み取りを一時停止し、ログアウト時は読み取り結果を破棄します。PaddleOCR・OpenCV・ONNX Runtimeなどのライセンス・著作権表示と、ソースの取得先案内は、配布物の `PhotoOcrAssets/notices/` に同梱しています（Dockerでは `/app/PhotoOcrAssets/notices/`）。リポジトリでは [third-party/photo-ocr/index.txt](third-party/photo-ocr/index.txt) を参照してください。

本の登録・編集では、識別コードの種類を「本の番号」にすると「ISBNから書籍情報を取得」を利用できます。入力済みの商品名・製造元・商品メモは上書きせず、出典を参考リンクへ追加します。出版社が未登録の場合は、必要に応じて作成・選択してください。カメラで読み取った場合も、書籍情報の取得はボタンで行います。

コレクションの「バーコード」→「カメラで読み取る」から、商品の所持状況を検索できます。有効なコードを確認するとカメラを終了して検索します。読み取りが難しい場合は数字を手入力してください。検索結果がない場合も、未登録の商品や別のコードで登録した商品が含まれるため、未所持とは限りません。

書籍情報は[国立国会図書館サーチAPI](https://ndlsearch.ndl.go.jp/help/api)で取得した国立国会図書館作成書誌を入力用に整形しています。通常書誌で見つからない場合は作成中書誌を検索します。取得内容を確認してから商品を保存してください。[書誌データの利用条件](https://www.ndl.go.jp/data/data_service/quickguide)も参照してください。この機能には、アプリのサーバーから `ndlsearch.ndl.go.jp` へのHTTPS通信が必要です。

ログインIDは「設定」→「アカウント設定」で変更できます。ID変更後も現在のログイン状態とパスキーは維持され、次回は新しいIDでログインします。

パスワード変更後は、すべての端末で再ログインが必要です。登録済みパスキーは保持します。パスキーの登録時には端末やパスワード管理アプリの操作画面が開きます。登録先サイトのURLは利用開始時に固定してください。

パスキーの認証・登録待ちは5分間、アプリ全体で128件まで保持します。期限切れは30秒ごとに削除し、上限に達した場合は既存の操作を保ったまま新しい開始を拒否します。しばらく待ってからやり直してください。

認証APIはアプリ全体で負荷を制限します。ログインや認証情報変更は60件/分・同時2件・待機2件、状態確認・CSRF取得等の読み取りは300件/分・同時8件・待機8件、本文は64KiBが初期値です。超過時は429（本文超過は413）を返します。`Authentication__Traffic__HeavyPerMinute`／`HeavyConcurrency`／`HeavyQueue`、同様の `ReadPerMinute`／`ReadConcurrency`／`ReadQueue`、`MaximumBodyBytes` で起動時に調整できます。送信元IP別の制限は配置側で行ってください。この全体上限だけでDDoS対策や利用者間の公平性を保証するものではありません。

パスワードの誤入力による5分間のロック中も、登録済みの有効なパスキーでログインできます。パスキーの使用によってパスワードのロックを解除することはありません。

運用ログには、認証成功・失敗・パスワードロック、パスワードやパスキー等の変更、全端末ログアウトを固定の `AUTH_` イベントで記録します。既知の利用者は内部の `UserId` で照合できます。パスワード・初期登録トークン・Cookie・認証器の公開鍵や署名・ログインID・入力した表示名は保存しません。失敗の繰り返しは先頭1件と60秒ごとの残件数で集計し、ユーザー別の集計枠は128件までとします。枠を超えた分はIDを保持せずイベント別に合算します。認証成功や認証情報変更は個別に記録し、従来のログ分割と保持期間を維持します。

「設定」→「アカウント設定」の「全端末からログアウト」で、現在の端末も含むログイン状態をまとめて解除できます。確認後に実行し、パスワードと登録済みパスキーは維持します。

ログインIDは英数字・`._-`の1～64文字で、大小文字を区別しません。パスワードは12～128文字で、NULは使えません。ログインを保持しない場合の認証上限は7日、保持する場合は30日です。5回連続でログインに失敗すると5分間停止します。

## 導入と設定

Linux x64のDocker・Docker Composeと、固定の公開HTTPS URLを用意します。単一コンテナ・単一インスタンスで利用します。

### Composeの準備

[compose-sample.yml](compose-sample.yml) を利用環境用の `compose.yml` へコピーし、プロキシのネットワークやラベルを設定します。[環境設定のサンプル](deploy/environment.example) は `.env` へコピーします。利用環境の `compose.yml` と `.env` はGit管理の対象外です。

```sh
cp compose-sample.yml compose.yml
cp deploy/environment.example .env
```

使用するDockerイメージを用意し、`.env` の値を配置先に合わせます。

| 項目 | 設定内容 |
| --- | --- |
| `GOODS_MANAGER_IMAGE` | 使用するイメージの固定版タグ、またはダイジェスト |
| `PUBLIC_ORIGIN` | パスキーの認証先サイトを指定する公開HTTPSオリジン。パス・クエリー・資格情報は含めない |
| `DATA_DIRECTORY` | データの保存先。コンテナ内 `/data` に接続 |
| `BACKUP_DIRECTORY` | バックアップの保存先。コンテナ内 `/backups` に接続 |
| `LOG_DIRECTORY` | ログの保存先。コンテナ内 `/logs` に接続 |
| `APP_UID` / `APP_GID` | 実行する非rootユーザーのUID/GID。初期値は各1654 |
| `APP_MEMORY` / `APP_CPUS` | メモリ・CPU制限。初期値は `2g` / `2` |

データ・バックアップ・ログの3箇所は、指定したUID/GIDで読み書きできるよう事前に作成します。Linuxホストで初期値を使う例：

```sh
sudo install -d -m 0700 -o 1654 -g 1654 /srv/goodsmanager/data /srv/goodsmanager/backups /srv/goodsmanager/logs
```

データ保存先にはDB・画像・認証鍵などが含まれます。コンテナを再作成しても同じ保存先を使い、`/data` 全体を永続化してください。稼働DBはローカルファイルシステムに置き、SMB/NFSで直接共有しない構成にします。

### HTTPS接続と起動

HTTPS終端、公開ホストによる振り分け、アプリのHTTP 8080への接続制限は配置側で設定します。アプリ側では公開URLのHTTPS・Host・ポートの一致を検査せず、プロキシIP・ネットワークの登録も行いません。サンプルはホストへポートを公開しません。共有ネットワークを使う場合は、接続済みの他のコンテナからも到達できるため、そのネットワーク内を信頼する構成で利用します。

プロキシは元のHostを保持し、`X-Forwarded-Proto: https` を付けて転送してください。アプリは直近1段のHTTPS情報だけを取り込みます。この情報はSecure CookieとCSRF保護に必要です。クライアントIP・Hostの転送ヘッダーは取り込みません。

`PUBLIC_ORIGIN` はプロキシの接続元を指定する設定ではなく、パスキーの認証先サイトを指定する設定です。公開URLのホストが固定のRP IDになるため、利用開始前にURLを固定します。Secure Cookie・CSRF保護と、パスキーの認証先の検証は引き続き有効です。

```sh
docker compose --env-file .env -f compose.yml config --quiet
docker compose --env-file .env -f compose.yml up -d --no-deps app
docker compose --env-file .env -f compose.yml ps
```

公開HTTPS URLへ接続し、初期登録画面でアカウントを作成します。

## バックアップ

バックアップは全コレクションと全アカウントをまとめて保全・復元する機能です。Web画面の操作はアプリ管理者に限ります。

自動バックアップは初期状態で有効で、日本時間の毎日03:00に実行します。「バックアップ」画面から有効・無効と実行時刻を変更できます。

- 初回は作成し、その後は保全対象に変更がなければ自動ZIPの作成を省略します。
- 実行時刻を過ぎて起動した場合は、その日の未実行分を1回処理します。失敗した場合は翌日、または手動で再実行します。
- 自動バックアップは成功した最新3世代を保持します。手動・更新前のバックアップは自動削除しません。
- バックアップには商品・所持品・ゴミ箱・参照中の写真・設定・認証鍵が含まれます。復元時には全端末のログイン状態が失効します。

ZIPは暗号化されません。認証に関する情報も含まれるため、保存先とダウンロードしたZIPを適切に保護し、外部への退避も行ってください。保存先は配置時の設定で指定し、Web画面からは変更できません。

## 更新

**コレクション対応前のDBは、この版へ移行できません。** 初期DB構造を作り直しているため、旧DBの移行履歴を検出した場合は起動を停止します。旧DB・画像・認証鍵・バックアップは削除せず保管し、この版は新しいデータ保存先で初期登録から開始してください。既存の保存先やDockerボリュームの削除は不要です。旧版のバックアップを確認・復元する場合は、その旧版を使用してください。

現在のイメージと設定を保管し、アプリを停止してバックアップを作成します。

```sh
docker compose --env-file .env -f compose.yml stop app
docker compose --env-file .env -f compose.yml run --rm --no-deps app backup create
```

作成成功と保存先を確認してから、`.env` のイメージを新しい固定版へ変更して取得・起動します。

```sh
docker compose --env-file .env -f compose.yml pull app
docker compose --env-file .env -f compose.yml up -d --no-deps app
```

起動時にDBの更新が必要な場合は、更新前バックアップの作成・検証後に移行します。バックアップや移行に失敗した場合は起動しません。更新後はログイン、商品・写真・所持数、バックアップを確認してください。

## バックアップからの復元

復元はアプリ停止中に行います。ZIPと互換性のあるアプリ版を使い、検証に成功してから復元します。

```sh
docker compose --env-file .env -f compose.yml stop app
docker compose --env-file .env -f compose.yml run --rm --no-deps app backup verify /backups/実行ID.zip
docker compose --env-file .env -f compose.yml run --rm --no-deps app backup restore /backups/実行ID.zip --confirm-replace
docker compose --env-file .env -f compose.yml up -d --no-deps app
```

復元後は全端末で再ログインし、画面を再読み込みします。復元前の結果不明な操作をそのまま再送せず、最新の内容を確認してから操作してください。

復元前のデータは `.rollback-*` に退避し、成功後も自動削除しません。空き容量を確保し、正常性と外部退避を確認してから整理します。古いアプリ版へ戻す場合も、その版と互換性のあるバックアップを復元してください。

復元途中の `restore-state.json` が残って起動できない場合は、停止したまま次を実行します。記録を手で削除しないでください。

```sh
docker compose --env-file .env -f compose.yml run --rm --no-deps app backup rollback --confirm-rollback
```

## ログインできない場合

パスワードの復旧は、アプリを停止した管理者が対話端末で行います。

```sh
docker compose --env-file .env -f compose.yml stop app
docker compose --env-file .env -f compose.yml run --rm --no-deps app recover-account --keep-passkeys
docker compose --env-file .env -f compose.yml up -d --no-deps app
```

`--keep-passkeys` は登録済みパスキーを保持します。削除する場合は `--clear-passkeys` を指定します。対象のログインIDを指定し、新しいパスワードは非表示で2回入力し、引数や環境変数には入れません。いずれの場合も対象アカウントの全端末のログインが失効し、ロックアウトが解除されます。

## 状態とログの確認

```sh
docker compose --env-file .env -f compose.yml exec app dotnet GoodsManager.Web.dll healthcheck
docker compose --env-file .env -f compose.yml logs --tail 100 app
```

ヘルス確認の終了コード0は準備完了、1は未準備です。Dockerの `unhealthy` 判定だけでは自動再起動しません。

公開監視には軽量な `/health/live` を使用してください。DB・保存先への書き込みを伴う `/health/ready` は公開リスナーでは404とし、コンテナ内の `127.0.0.1:8081` の別リスナーだけで提供します。Dockerのヘルス確認コマンドはこの内部リスナーへ接続します。内部ポートは `Operations__HealthPort` で変更可能ですが、ポートを公開したり、リバースプロキシから中継したりしないでください。通常の公開ポートや開発用HTTPSの起動URLとは独立しています。

ログは標準出力と `/logs` に保存します。アプリのファイルログは日次分割・1ファイル50MB・30暦日保持です。ログ・手動バックアップ・更新前バックアップ・復元退避を含め、保存領域の空き容量を確認してください。
